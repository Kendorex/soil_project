# Многополевая оптимизация откалиброванной модели

Основной вход: `python run_optimizer.py inspect|validate|prepare|baseline|historical|optimize`.
[Результаты выполненных проверок](MULTIFIELD_VERIFICATION.md).
[Диагностика культур и сценария 2023](CROP_DIAGNOSTICS_2023.md).
`run_multifield.py` предоставляет те же команды. Прежние флаги `--calibrate-cultivar`,
`--optimize-nsga2` и другие оставлены для прежних экспериментов; они используют старую постановку.

## Запуск на этом компьютере

Установленный APSIM находится в WSL: `/home/user/ApsimX/bin/Release/net8.0/Models`.
Из PowerShell:

```powershell
wsl -e bash -lc 'cd /mnt/c/Users/user/Desktop/APSIMX_Main_Task/ApsimOptimization_Work_in_prog && python3 run_optimizer.py inspect'
wsl -e bash -lc 'cd /mnt/c/Users/user/Desktop/APSIMX_Main_Task/ApsimOptimization_Work_in_prog && . .venv/bin/activate && python3 run_optimizer.py baseline'
```

Для другого компьютера: Python 3.10+, `pip install -r requirements.txt`, установленный
APSIM Next Generation с поддержкой версии 216 и SWIM3. В `runtime.command` задаётся
список аргументов: `["/path/to/Models"]` или `["dotnet", "/path/to/Models.dll"]`.
Запускайте Python в той же ОС, где работает APSIM. Пути модели, погоды и выходов
разрешаются относительно файла конфигурации. CLI APSIM запускается без shell.

После заполнения `configs/multifield.yaml`:

```bash
python3 run_optimizer.py validate
python3 run_optimizer.py optimize
python3 -m pytest tests/test_multifield.py -q
```

Для короткой проверки можно переопределить размер запуска без правки YAML:

```bash
python3 run_optimizer.py optimize --config configs/multifield_2023_n_diagnostic.yaml \
  --population 4 --generations 1
```

После smoke-проверки диагностический фронт можно расширить. Сценарий ниже выполняет
тесты, запуск 12 × 3, упаковку и проверку архива:

```bash
APSIM_MODELS=/absolute/path/to/Models \
  bash scripts/run_multifield_pareto_check.sh
```

Размер можно переопределить, например
`POPULATION=20 GENERATIONS=5 bash scripts/run_multifield_pareto_check.sh`.

`inspect` работает и при незаполненных доменных параметрах. `validate` возвращает
код 2 и полный перечень отсутствующих значений. `prepare --year ...` создаёт базовую
CLI-копию без запуска APSIM. `baseline --year ...` рассчитывает исходное удобрение,
без выдуманной экономики. `optimize` требует заполненной и подтверждённой конфигурации.
Код 3 означает, что допустимых решений нет; пустой фронт не выдаётся за успех.

## Исторический пример 2022–2023

В `configs/multifield.yaml` выбран урожайный 2023 год, а включительное окно решений
задано от 2022-09-01 до 2023-12-31. Осень 2022 года входит в задачу, потому что
озимая рожь на Field5 и Field9 посеяна 2022-09-05. Урожай, прибыль и почвенное
состояние оцениваются за 2023 год. Фактическое размещение культур остаётся заданным
севооборотом APSIM; выбор культур будет отдельным следующим этапом планирования.

Наблюдения из листа `Фенофазы` сохранены в
`data/observations/historical_2022_2023.json`. Запись 2022 года для Field9 в
источнике отсутствует, но в 2023 году представлены все десять полей. После
`baseline` автоматически создаются `historical_comparison.json` и
`historical_comparison.csv`. Для уже готового результата сравнение можно повторить:

```bash
python3 run_optimizer.py historical --year 2023 \
  --results outputs/multifield/baseline_<id>/baseline.json
```

Сравнение использует зерно овса для записей «овёс с подсевом трав», зерно Wheat
для яровой пшеницы и модели озимой ржи, сумму RedClover и PlantainForage для
травосмеси. Эти компоненты заданы явно в файле наблюдений. Текущий APSIMX хранит
`Area=1.0` для каждой зоны, а агрегация использует пользовательскую оценку 0,2 га
на участок из конфигурации. Общая расчётная площадь равна 2 га. Итоги по массе
остаются приблизительными, пока участки не обмерены.

## Что изменено в модели

Указанный пользователем APSIMX сохранён неизменяемым снимком в `simulation/source/`.
Скрипт `scripts/build_multifield_calibrated_v2.py` переносит в него подтверждённую
финальную калибровку Zlata и фенологию озимой ржи, проверяет Irgina относительно
принятой модели и создаёт
`simulation/calibrated/full_field2019_2023_calibrated_v2.apsimx`. Полный список
изменений и SHA-256 записан в соседнем provenance-файле. Актуальный источник уже
содержит полные параметры менеджеров севооборота, поэтому внешний reference-файл
при подготовке рабочих копий не используется. Исправленная погода отличается от
пользовательского MET только переводом давления из hPa в заявленные Pa и
пересчётом `tav/amp`; это также зафиксировано отдельным provenance-файлом.

Рабочая копия исключает менеджеры `Synchroniser`, требующие внешнего ZMQ-сервера,
удаляет пустые выражения Report и использует локальную `weather.met`.
Начало Clock остаётся 2019-01-01: обрезание истории сдвинуло бы индексы севооборота.
Оптимизация заменяет исходные внесения внутри `decision_period`, включая осень
предыдущего календарного года; внесения до и после этого окна сохраняются. Каждый
кандидат получает собственную папку, APSIMX, БД и журнал.

Поля, площади, культуры, севообороты и исходные Report обнаруживаются из дерева модели.
Область поддержки — одна Simulation с несколькими Zone, как в предоставленном файле.
Новая культура с неизвестным органом урожая вызывает явную ошибку и требует адаптера.

## Цели и ограничения

NSGA-II из `pymoo` использует смешанные переменные: категорию продукта/смеси и
вещественную дозу для каждого поля. Дозы с одинаковыми границами фиксируются.

1. Максимум суммарного урожая выбранных продуктов за урожайный год, кг сухого вещества.
   По полям суммируются `yield_kg_dm_ha × area_ha` только для культур из
   `objective_yield_components`. Это общий физический показатель
   сухого вещества разных культур; он не является средней урожайностью зерна или
   свежей массой картофеля. Выбор `yield_aggregation: total_harvest_dry_matter_kg`
   должен быть явно подтверждён пользователем.
2. Максимум чистой прибыли по всем полям в указанной валюте.
3. Минимум суммарного нормированного выхода почвенных показателей за интервалы.
   Внутри допустимых интервалов третья цель равна нулю: произвольное «лучшее»
   значение внутри диапазона не вводится.

Для каждой пары поле/элемент можно задать только `min`, только `max` или интервал.
Для интервала: `g_low=(min-observed_min)/(max-min)` и
`g_high=(observed_max-max)/(max-min)`. Для односторонней границы нормирование
выполняется на абсолютную величину ненулевого порога; поле `normalization_scale`
позволяет явно задать другой положительный масштаб. При
`soil_constraint_mode: hard` величины также передаются как реальные ограничения
`G <= 0` в pymoo. Это режим производственной конфигурации с подтверждёнными
агрономическими интервалами. При `soil_constraint_mode: objective_only` они входят
только в третью цель; диагностический запуск использует этот режим, чтобы показать
компромиссы при неподтверждённых baseline-порогах. Ограничения `dose_ratios`
остаются жёсткими в обоих режимах. Третья цель — сумма положительных частей
нормированных отклонений.
Проверка выполняется ежедневно (`period: daily`) либо на точную дату (`period: date`).
Обязательна хотя бы одна конечная граница, для интервала `min < max`, а также
единицы, описание глубины и скалярное выражение APSIM. Массив по слоям нужно свести
выражением к требуемому показателю.

Пример структуры, **без рекомендуемых чисел**:

```yaml
nutrients:
  - name: mineral_n
    expression: sum([NO3].kgha) + sum([NH4].kgha)
    unit: kg/ha
    depth_description: весь профиль
    min: null
    max: null
    period: date
    date: null
```

Исходный Report называет MineralN сумму NO3+NH4+Urea. Новый диагностический
`MineralN_NO3_NH4` исключает мочевину; `UreaN` выводится отдельно. Порог для всего
профиля в кг/га нельзя подменять порогом мг/кг для верхнего слоя. P/K не имитируются
фиктивно: для их оптимизации модель должна реально рассчитывать соответствующие
пулы и отклик на внесение. Неразрешимые Report/API-выражения приводят к ошибке APSIM.

## Дозы, смеси и даты

`fields.<field>.area_ha` — фактическая площадь участка для агрегации урожая,
доходов и затрат. Она обязательна и не подменяется текущим `Zone.Area=1.0`.
`objective_yield_components` явно задаёт, какие активные в выбранном году культуры
образуют урожай и выручку данного участка.

`fields.<field>.dose_kg_product_ha` — масса продукта/смеси на гектар **на одно
внесение**. `application_dates` — фиксированные уникальные ISO-даты внутри
`decision_period`,
одна и та же доза в каждую дату; `application_depth_mm` задаётся явно. Это позволяет
управлять удобрением многолетних трав даже в год без посева. Даты на первом этапе
не оптимизируются. Нулевая доза не создаёт прохода и затрат на внесение.

`fertilizer_options` — пользовательский каталог. Каждый вариант содержит цену
единицы массы смеси и список компонентов:

```yaml
fertilizer_options:
  approved_product:
    price_per_kg_product: null
    components:
      - apsim_type: NO3N
        mass_fraction: null
        apsim_amount_per_kg_product: null
```

Сумма `mass_fraction` равна 1. Фактический аргумент APSIM Apply = доза смеси ×
массовая доля × `apsim_amount_per_kg_product`. Например, типы APSIM `NO3N` и
`NH4NO3N` описывают азот; коэффициент нельзя считать равным единице для любого
товарного удобрения. Его задают по составу продукта и определению FertiliserType.
Каталог можно наполнить несколькими явно согласованными соотношениями компонентов:
выбор смеси — категориальная переменная, её общая доза — непрерывная.

`dose_ratios: []` явно означает отсутствие ограничений между дозами разных полей.
Иначе задаются `numerator_field`, `denominator_field`, `min`, `max` для отношения
доз продукта на одно внесение. Минимальная доза поля-знаменателя должна быть > 0.
Это отдельная возможность; соотношения компонентов смеси задаются выше.

## Урожай и экономика

На каждое поле/культуру создаётся отдельный `OptHarvest_<field>_<crop>` Report,
подписанный на `[Crop].Harvesting` (до `PostHarvesting` и удаления биомассы).
Зерновые/рапс/горчица используют `Grain.Total.Wt`, картофель — `Tuber.Total.Wt`,
клевер и PlantainForage — `AboveGround.Wt`; множитель 10 переводит г/м² в кг/га.
Суммируются события данного года, а не максимум дневного Report. Смешанные посевы
учитываются по компонентам без повторного добавления `MixYield`.

Это масса органа перед уборкой. Для выручки обязательный коэффициент
`marketable_kg_per_kg_dm` переводит её в реализуемую массу с учётом влажности,
доли фактического изъятия и потерь. Он может быть нулём для непродаваемой культуры.
Нельзя применять цену свежего картофеля непосредственно к его сухой массе.

На гектар:

`revenue = Σ(yield_dm × marketable_kg_per_kg_dm × price_per_kg)`

`net_profit = revenue - applied_product × price_per_kg_product - passes × application_cost_per_ha - other_cost_per_ha`

`other_cost_per_ha` — все остальные затраты выбранного года, включая семена,
операции, уборку, постоянные расходы и финансирование, если они учитываются.
Пользователь должен указать их полностью; значения старого пшеничного проекта
не переносятся. Фактические масса внесения и число проходов считываются из Report
и сверяются с решением до расчёта прибыли.

Если две реальные продукции используют один APSIM-компонент (сейчас яровая
пшеница и озимая рожь обе представлены как `Wheat`), поле
`fields.<field>.product_economics` переопределяет общую цену и коэффициент именно
для этого участка.

Список значений, которые ещё требуется подтвердить для производственного запуска,
сведён в [INPUTS_REQUIRED_2023.md](INPUTS_REQUIRED_2023.md).

Отсутствующая уборка ожидаемой культуры, NaN, NULL, отрицательная масса, неполный
год ежедневных данных, ошибки APSIM и превышение времени не становятся нулевым
урожаем. Кандидат получает статус failed и исключается из допустимого фронта.
Нулевой урожай при существующем событии уборки допустим. Строгая проверка отсутствия
уборки также отклоняет гибель культуры; её нельзя незаметно считать доходом 0.

## Сценарии погоды и водного режима

Оптимизатор поддерживает несколько подтверждённых вариантов среды для одного
управленческого решения. Каждый элемент `environment_scenarios` имеет безопасное
уникальное имя и при необходимости переопределяет `model`, `weather` или
`rotation_parameter_reference`. Пути разрешаются относительно YAML. Структура
полей, площади, культуры, севооборот и исходные внесения должны совпадать с
основной моделью; смешивание другого управления со сценарием среды отклоняется до
запуска NSGA-II.

```yaml
environment_scenarios:
  - name: calibrated_baseline
scenario_aggregation:
  yield: mean
  profit: mean
  soil: worst_case
```

Текущие конфигурации содержат только откалиброванную основную модель. Второй
сценарий не добавлен, поскольку подтверждённого альтернативного водного режима или
погоды пока нет. Для нескольких сценариев правила агрегации обязательны. `mean`
для урожая и прибыли означает среднее с равными весами; `worst_case` означает
минимум. Почвенное отклонение всегда берётся по худшему сценарию, а жёсткие
ограничения должны выполняться в каждом сценарии.

В `evaluations.json` сохраняются полные результаты каждого сценария, агрегированные
цели и диапазоны `*_range`. В CSV имеются минимум и максимум общих показателей и
показателей каждого поля. Поэтому после добавления подтверждённых вариантов можно
строить графики устойчивости решения без повторного разбора SQLite.

## Результаты и воспроизводимость

### История качества модели

После каждого изменения модели сначала выполняется baseline, затем:

```bash
python3 scripts/record_multifield_quality.py \
  --baseline outputs/multifield/DIAGNOSTIC_2023_N/baseline_<id> \
  --label short_change_name \
  --notes "что именно изменено и почему"
```

Checkpoint сохраняет хеши исходной и подготовленной модели, погоды, БД и набора
наблюдений. Каталог `outputs/multifield/quality_history/checkpoints/<id>/`
неизменяем и содержит `summary.json`, `field_metrics.csv`, `crop_trace.csv` и
`management_mismatches.csv`.

Полная историческая проверка выполняется так:

```bash
python3 scripts/evaluate_historical_replay.py --run
```

Файл `decision_readiness.json` проверяет независимый 2023 год без придуманного
абсолютного порога ошибки. Требуются 100% покрытия и событий уборки, RMSE ниже
простого прогноза средним урожаем за 2019–2022 годы и положительная корреляция
Spearman между полями. До выполнения всех условий результаты NSGA-II считаются
инженерной диагностикой, а не рекомендацией для размещения культур.

Для овса предусмотрен отдельный заблокированный по времени опыт:

```bash
python3 scripts/calibrate_oats_yield_components.py --run
```

Он использует только точные сочетания массы и числа зёрен из локального
`Models/Resources/Oats.json`, выбирает профиль по 2019–2022 годам и один раз
проверяет его на 2023 годе. Все кандидаты, параметры, хеши и crop-level метрики
сохраняются в `outputs/multifield/OATS_YIELD_CALIBRATION/<timestamp>/` и в общей
истории checkpoint-ов.

После отклонения профилей массы и числа зёрен проверка листового аппарата и
кущения выполняется отдельно:

```bash
python3 scripts/calibrate_oats_canopy_structure.py --run
```

Опыт сохраняет фенологические команды Yakov и сравнивает только дискретные
canopy/branching-команды, дословно взятые из Drummond и Milton локального
`Models/Resources/Oats.json`. Выбор также выполняется на 2019–2022 годах, а 2023
год используется для независимого принятия или отклонения. Результаты находятся
в `outputs/multifield/OATS_CANOPY_CALIBRATION/<timestamp>/`; исходная модель при
этом не изменяется.

Для графиков подготовлены объединённые таблицы:

- `index.csv` — RMSE, полнота расчёта и подпись каждого этапа;
- `overall_history.csv` — MAE, RMSE, bias, R² и корреляция;
- `paired_history.csv` — честное сравнение каждого этапа с первым checkpoint
  только на общих успешно рассчитанных наблюдениях;
- `field_history.csv` — наблюдение, расчёт, ошибка и фенология по полю/году;
- `crop_history.csv` — динамика качества отдельно по группам культур.

При изменении полноты нельзя сравнивать обычный RMSE между этапами: новый трудный
случай способен увеличить RMSE при исправлении программы. Для такого сравнения
используется `paired_history.csv`, а полнота строится отдельно из `index.csv`.

Политика `rotation_transition_policy: harvest_on_winter_sowing_proxy` устраняет
потерю события уборки, когда поздний укос многолетних трав пересекается с более
ранним посевом следующей озимой культуры. Фактическая дата укоса неизвестна,
поэтому это явно обозначенный диагностический proxy. Производственная конфигурация
оставляет выбор политики незаполненным до подтверждения.

`outputs/multifield/<action>_<id>/` содержит снимок конфигурации, инвентаризацию
модели с SHA-256 источников, каталоги кандидатов и:

- `pareto.json` — допустимый недоминируемый фронт по всем оценённым кандидатам;
- `evaluations.json` — все уникальные решения, цели, ограничения, экономика полей,
  наблюдаемые интервалы почвы и ошибки;
- `pareto_summary.csv` — компактная таблица фронта с решениями и результатами полей;
- `evaluations_summary.csv` — такая же таблица для всех проверенных кандидатов;
- `plots/pareto_objectives.png` — урожай и прибыль всех кандидатов с цветом
  почвенного отклонения и выделенным Pareto-фронтом;
- `plots/pareto_doses.png` — дозы и типы удобрения по полям для каждого решения
  Pareto;
- `plots/pareto_plots_manifest.json` — хеши источников построенных графиков;
- `history.json` — порядок оценок и попадания в кэш внутри запуска;
- `candidates/<hash>/environment_scenarios/<name>/candidate.apsimx`, `candidate.db`
  и `apsim.log`; общий результат кандидата находится в
  `candidates/<hash>/result.json`.

Кэш ограничен одним запуском: изменённые погода, калибровка или экономика не могут
получить результат прежнего запуска. Единственный «лучший» вариант не назначается
без правила выбора компромисса пользователя. Сохраняется весь фронт.

Необязательный `reference_decision` задаёт известный опорный вариант. Он всегда
оценивается до случайной популяции и включается в общий поиск недоминируемых
допустимых решений. Это важно, когда допустимая область узкая. Даже при пустом
фронте `pareto.json` содержит три успешных решения с минимальным суммарным
нарушением ограничений.

Тест `scripts/verify_multifield_runtime.py --run` — отдельный сквозной инженерный
тест реального APSIM с искусственной экономикой и диагностическими интервалами.
Его результаты в `ENGINEERING_ONLY_*` не являются агрономическими рекомендациями
и не изменяют `configs/multifield.yaml`.

Причины текущих расхождений и результаты изолированных опытов приведены в
[FIELD_ERROR_DIAGNOSTICS.md](FIELD_ERROR_DIAGNOSTICS.md).

`configs/multifield_2023_n_diagnostic.yaml` — воспроизводимый N-only сценарий.
Его дозы взяты из модельной дозы и исторических меток N30/N60, почвенные нижние
границы — из baseline 2023, экономика — из старых файлов проекта. В конфигурации
он явно помечен `scenario.kind: diagnostic` и не должен использоваться для
агрономической или финансовой рекомендации. Baseline-границы в нём оцениваются
через третью цель и не отбрасывают варианты с отличающимся конечным запасом N.

Алгоритм и смешанные операторы: [NSGA-II](https://pymoo.org/algorithms/moo/nsga2.html),
[Mixed variables](https://pymoo.org/customization/mixed.html).
