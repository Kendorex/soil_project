# Логика APSIMX-оптимизации

## 1. Назначение

Проект предназначен для выбора экономически эффективной технологии яровой
пшеницы. Технологии сравниваются по средней прибыли, управляемым затратам и
прибыли в неблагоприятном погодном сценарии.

APSIMX и NSGA-II выполняют разные функции:

- APSIMX моделирует развитие культуры и рассчитывает урожайность;
- `pymoo` NSGA-II предлагает и сравнивает технологии;
- Python создаёт модели, запускает APSIMX, читает SQLite, рассчитывает
  экономику и возвращает цели в NSGA-II.

## 2. Общая последовательность

```text
optimizer_config.yaml и входные файлы
→ пространство допустимых технологий
→ кандидат NSGA-II
→ декодирование параметров
→ временные APSIMX-копии по погодным сценариям
→ dotnet Models.dll
→ SQLite Report
→ урожайность, экономика и дополнительные outputs
→ f1, f2, f3
→ следующее поколение NSGA-II
```

Это итерационная связка `pymoo ↔ APSIMX`. Режим NSGA-II не использует заранее
рассчитанный full-grid как источник оценок.

## 3. Технология и пространство поиска

Одна технология представляется как:

```text
x = (d_sow, cultivar, population, depth, row, fertilizer_scheme)
```

- `d_sow` — дата или правило посева;
- `cultivar` — сорт;
- `population` — число растений на квадратный метр;
- `depth` — глубина посева, мм;
- `row` — междурядье, мм;
- `fertilizer_scheme` — готовая дискретная схема удобрения.

Удобрение не раскладывается на независимые N/P/K-переменные. Каждая схема
содержит APSIMX-тип, дозу, правило срока внесения и число проходов.

Основная конфигурация:

| Ось | Значения |
|---|---|
| Посев | `1-may..30-may`, фиксировано |
| Сорт | `Zlata`, `Irgina` |
| Population | 250, 300, 350, 400, 450, 500 |
| Глубина | 20, 30, 40, 50, 60 мм |
| Междурядье | 125, 150, 250 мм |
| Удобрение | 29 готовых схем |

Получается 5220 технологий. При трёх активных сценариях полный перебор требует
15660 APSIMX-прогонов.

Демонстрационная конфигурация ограничивает пространство до 64 технологий:
два сорта, два population, две глубины, два междурядья и четыре схемы
удобрения. NSGA-II оценивает не более 12 кандидатов за два поколения.

## 4. APSIMX-шаблон и погода

Используется один базовый файл:

```text
simulation/standart.apsimx
```

В текущей версии шаблона площадь расчётной Zone равна `1.0` га. Экономические
результаты проекта также представлены в расчёте на гектар.

Для каждой пары `technology × scenario` Python создаёт отдельную копию:

```text
outputs/.optimizer_work/<mode>/<technology_id>/<scenario_id>.apsimx
```

В копию подставляются weather-файл, сорт, правило посева, population, глубина,
междурядье и схема удобрения. Исходный `standart.apsimx` не изменяется.
`scenario_id` определяет погоду и имена выходных файлов, но не выбирает
отдельный APSIMX-шаблон.

Настроены четыре погодных сценария. Сейчас активны:

```text
s1_dojdey
s3_norm
s4_zasuha
```

`s2_holod` сохранён, но временно имеет `enabled: false`. Поэтому `profit_avg`
и `profit_min` сейчас рассчитываются по трём сценариям.

## 5. Один APSIMX-прогон

Для отдельной технологии и сценария:

1. создаётся временная `.apsimx`;
2. удаляется старая `.db`, если она существует;
3. APSIMX запускается через `dotnet Models.dll`;
4. проверяется завершение процесса и появление `.db`;
5. читается таблица SQLite `Report`;
6. извлекаются урожайность и доступные nitrogen/soil outputs;
7. рассчитывается экономика;
8. результат сохраняется в CSV и cache.

Отсутствие `.db`, таблицы `Report` или колонки Yield является технической
ошибкой. Если Yield существует, но пригодного ненулевого значения нет, это
трактуется как неурожайный сценарий:

Нулевая урожайность не считается автоматически успешным результатом. Строгая
политика различает:

```text
invalid_not_sown       культура не была посеяна
invalid_no_harvest     посев был, но HarvestRipe не достигнут
rejected_zero_yield    HarvestRipe достигнут, но Yield равен нулю
completed              жизненный цикл и ненулевая урожайность подтверждены
```

Первые три состояния не передаются в экономику как обычный успешный прогон.

## 6. Правило чтения урожайности

Reader ищет точную колонку из настроенного списка:

```text
Yield
GrainWt
Wheat.Yield
```

Предпочтительно используется последняя строка стадии `HarvestRipe`. Если такой
строки нет, выбирается последняя ненулевая урожайность. При полном отсутствии
урожая используется последняя строка Report для диагностики состояния
культуры и почвенных outputs. В текущей конфигурации Yield ожидается в кг/га и
переводится в т/га.

Дополнительно по всему `Report` определяются события посева и уборки,
максимальные LAI и биомасса. Поэтому нормальное завершение APSIMX-процесса само
по себе больше не означает успешный агрономический результат. Та же проверка
применяется к базе после Run в GUI командой
`python3 scripts/validate_apsim_run.py path/to/prepared_run.apsimx`.

Готовый переносимый файл для GUI и `run_manifest.json` создаются через
`--prepare-gui-run`. Ручное изменение Clock в базовом шаблоне не является
поддерживаемым способом воспроизведения сценария.

## 7. Экономика

```text
C_material = sum(price(type) × amount)
C_application = application_cost × fertilizer_passes
C_finance = finance_rate × finance_days / 365 × C_material

controllable_cost = C_material
                    + C_application
                    + C_finance
                    + seed_cost_adjustment
```

Прибыль сценария:

```text
profit = grain_price × Yield
         - constant_C
         - controllable_cost
         - (harvest_variable_cost + cleaning_cost + handling_cost) × Yield
```

Основные значения из `data/economics/economic_constants.csv`:

| Параметр | Значение |
|---|---:|
| Цена зерна | 14300 руб./т |
| Постоянная статья | 23000 руб./га |
| Внесение | 480 руб./га за проход |
| Очистка | 500 руб./т |
| Погрузка и перевалка | 350 руб./т |
| Ставка финансирования | 0,18 в год |
| Период финансирования | 240 дней |

`constant_C` входит в прибыль, но не входит в `controllable_cost`, поскольку
не зависит от выбора технологии. Параметры стоимости семян пока имеют статус
`provisional`.

## 8. Агрегация по сценариям

Одна и та же технология запускается по всем активным сценариям:

```text
profit_avg = mean(profit_s1, profit_s3, profit_s4)
profit_min = min(profit_s1, profit_s3, profit_s4)
```

`profit_avg` характеризует средний экономический результат, `profit_min` —
устойчивость технологии к худшей из рассматриваемых погодных ситуаций.

## 9. NSGA-II

Кандидат кодируется шестью индексами:

```text
[date_idx, cultivar_idx, population_idx, depth_idx, row_idx, fertilizer_idx]
```

Значения округляются и ограничиваются допустимыми границами, после чего
декодируются в технологию.

Целевые функции:

```text
f1 = -profit_avg
f2 = controllable_cost
f3 = -profit_min
```

`pymoo` минимизирует цели, поэтому максимизируемые прибыли передаются со
знаком минус.

Внутри каждого вызова evaluator кандидат декодируется, технология запускается
в APSIMX по активным сценариям, результаты агрегируются и цели возвращаются в
`pymoo`. После этого NSGA-II формирует следующее поколение.

Остановка определяется числом поколений из config. Автоматической остановки
по сходимости Парето-фронта пока нет. Если APSIMX или SQLite дают фатальную
ошибку, кандидат получает большой штраф вместо остановки всего NSGA-II.

## 10. Парето-фронт

NSGA-II возвращает набор недоминируемых решений. Для каждого из них нельзя
улучшить один критерий без ухудшения хотя бы одного другого.

В `best_solution.json` сохраняются:

- `best_by_profit_avg` — максимальная средняя прибыль;
- `best_by_lowest_controllable_cost` — минимальные управляемые затраты;
- `best_compromise_solution` — нормализованный компромисс трёх целей.

## 11. Full-grid

`--full-grid` последовательно оценивает все технологии из config. Он полезен
как контроль на небольшом пространстве, но не является основой NSGA-II.

- full-grid проверяет каждую комбинацию и требует много времени;
- NSGA-II направленно исследует часть пространства;
- короткий NSGA-II не гарантирует нахождение абсолютного оптимума.

## 12. Nitrogen и soil outputs

Reader поддерживает дополнительные колонки:

```text
MineralN, MineralNWithUrea, NO3kgHa, NH4kgHa, OrganicC,
DenitrifiedN, NAtmosphereLoss, NO3Leaching
```

Основной показатель минерального азота определяется так:

1. используется `MineralN`, если он существует;
2. иначе рассчитывается `NO3kgHa + NH4kgHa`;
3. `MineralNWithUrea` не используется без явного разрешения в config.

Дополнительные outputs не блокируют экономическую оптимизацию. Их статус:
`available`, `partial` или `missing`.

## 13. Почвенные ограничения

Постановка содержит:

```text
N_NO3 >= 4 мг/кг
P_2O5 >= 51 мг/кг
SOC_end >= SOC_0
```

Эти ограничения не включаются автоматически. `MineralN` в кг/га нельзя без
обоснованного пересчёта считать `N_NO3` в мг/кг; `OrganicC` не является
автоматической заменой SOC; любой phosphorus pool APSIMX нельзя считать
`P_2O5` по Кирсанову.

Без точных подтверждённых данных:

```text
constraints_status = soil_constraints_unchecked
is_feasible = null
```

Текущая безопасная конфигурация использует `strict: false` и
`source: disabled`. Технически работающее Reporter expression не активирует
ограничение без агрономического подтверждения.

## 14. Cache и ошибки

Ключ cache учитывает технологию, сценарий и сигнатуры входных файлов. Если
валидный результат уже существует, APSIMX повторно не запускается. Флаг
`--ignore-cache` принудительно выполняет новые сценарные прогоны.

При фатальной ошибке отдельного сценария NSGA-II получает штраф, а сведения об
ошибке сохраняются. Один ошибочный кандидат не останавливает оптимизацию.

## 15. Выходные файлы

- `results_runs.csv` — отдельные сценарные прогоны;
- `results_technologies.csv` — агрегированные технологии;
- `all_results.csv`, `feasible_results.csv`, `rejected_results.csv`,
  `top_20_solutions.csv` — результаты full-grid;
- `nsga2_evaluations.csv` — кандидаты NSGA-II и цели;
- `pareto_nsga2.csv` — Парето-фронт;
- `best_solution.json` — выбранные решения;
- `optimizer_log.txt` — поколения, кандидаты, APSIMX runs и cache;
- `validation_report.txt`, `validation_report.json` — проверка полного набора
  результатов.

## 16. Калибровочные режимы

Калибровка сортов и начальной влажности отделена от экономической
оптимизации. Её config-файлы используют полевые материалы:

```text
docs/20260804_ВНИИМЗ_трансекта/20260804_ВНИИМЗ_трансекта.xlsx
```

Калибровка изменяет только временные копии APSIMX. Текущая `Irgina` имеет
предварительную фенологическую калибровку; это не равнозначно полной
калибровке урожайности.

## 17. Основные команды

```bash
python3 run_optimizer.py --check-env
python3 run_optimizer.py --dry-run
python3 run_optimizer.py --single-run --scenario s3_norm --scheme F0_no_fertilizer
python3 run_optimizer.py --evaluate-technology --scheme F0_no_fertilizer
python3 run_optimizer.py --full-grid --allow-large-grid
python3 run_optimizer.py --optimize-nsga2
python3 run_optimizer.py --diagnose-soil-outputs
python3 run_optimizer.py --test-soil-output-candidates --scenario s3_norm
python3 run_optimizer.py --validate-outputs
```

Для короткой проверки используется `configs/optimizer_config_demo.yaml`.

## 18. ZeroMQ

Основной evaluator сейчас запускает APSIMX через `Models.dll`. Для будущего
ZeroMQ-запуска подготовлен `tools/zmq_oneshot.py`:

```text
dotnet ApsimZMQServer.dll --file model.apsimx -P oneshot --port 5555
```

FSM, суточные барьеры и ручная синхронизация не используются. Узел
`Synchroniser` в `standart.apsimx` отключён.

## 19. Ограничения текущего состояния

- APSIMX runtime доступен и проверяется в Ubuntu WSL, а не в Windows Codex.
- `s2_holod` отключён до отдельной проверки двух сортов.
- Soil constraints остаются unchecked до подтверждения точных данных.
- Экономика семян использует предварительные параметры.
- Основная конфигурация вычислительно тяжёлая; для демонстрации следует
  использовать `optimizer_config_demo.yaml`.
